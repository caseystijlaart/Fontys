= Candidate Embedded Platforms

The IWR6843AOPEVM's own onboard DSP and Cortex-R4F already run TI's people-tracking firmware and produce a tracked point-cloud stream (<<tidue71d>>, <<mmwavesdkug>>); the host board this chapter picks does not run the mmWave SDK itself.
Its job is narrower: consume that stream, run the classification stage, and expose the result to the Holobox pipeline.
Barral et al. (<<barral2024mmwaveiot>>) document exactly this split on the same radar family: TI's onboard firmware handles point-cloud generation and a first-pass extended-Kalman-filter track, while their paired host runs the downstream filtering, clustering, and output stack.

[[mcu-baseline]]
== Bare-Metal MCU

Finance and Risks' own risk table already names an MCU-to-Linux-SBC fallback direction, implying the project could in principle start at the MCU tier.
A representative part, the ESP32-S3, is cheap (a few euros) and has built-in WiFi, but no gathered source pairs an MCU-class part with this radar family for point-cloud consumption, and running the sensor's output parser, a classification stage, and later the microphone array's beam-steering concurrently is a level of scheduling and memory management an MCU without a real OS is not well suited to for this project's timeline.
This tier is ruled out as a starting point rather than attempted first and abandoned; the project starts directly at the Linux single-board-computer (SBC) tier the risk table already anticipates.

[[rpi4]]
== Raspberry Pi 4 Model B (4GB/8GB)

A quad-core Cortex-A72 @ 1.5GHz, Gigabit Ethernet, dual-band WiFi, and USB 3.0/2.0, sold in 2GB (€60.49), 4GB (€108.89), and 8GB (€157.29) RAM variants at current link:https://www.kiwi-electronics.com/en/raspberry-pi-4-model-b-8gb-10032[Kiwi Electronics] (NL) listings, all sharing the same CPU and interfaces.

The 4GB variant is the one carried forward.
The primary design does not need a ROS-based stack at all (Barral et al.'s ROS overhead was that paper's own architecture, not a requirement of this one), and classification itself is expected to run in the IWR's own onboard firmware rather than on the host, per Introduction; the host's own job reduces to receiving a small already-classified result over UART, running the microphone array's beam-steering, and bridging both to the network.
None of that approaches a 4GB ceiling, so there is no overhead case for paying for 8GB up front.
Neither literature source below reports which RAM variant it used, so precedent does not favour one variant over another either way.
The one scenario that would actually need more memory, the raw point cloud plus a PyTorch runtime for the ProbRadarM3F fallback, is also a CPU-throughput problem, not just a memory one; if it is ever triggered, escalating to the Raspberry Pi 5 (Recommended Approach) addresses both at once, rather than buying 8GB of RAM on this board now against a scenario that, if it happens, calls for a faster CPU anyway.

This is the only candidate with a literature precedent for the exact combination this project plans to use: Barral et al. (<<barral2024mmwaveiot>>) pair an IWR6843ISK, the same radar family as the already-selected IWR6843AOPEVM, with a Raspberry Pi 4 over USB, running TI's onboard tracking firmware on the radar and a downstream ROS-based clustering/tracking/output stack on the Pi.
Huang et al. (<<huang2021mmwave>>), already cited in Candidate Sensor Technologies, separately show real-time multi-person mmWave tracking running on the same board.

Barral et al. also report a concrete open risk worth carrying into the bench-testing stage: they note bandwidth constraints extracting measurements over the USB interface at higher data rates.
This project's own point-cloud rate has not been measured yet, so whether that constraint applies here is unconfirmed, not ruled out.

Pros::
* Only candidate with a literature precedent for this exact radar-family-plus-host combination (Barral et al.).
* Separate real-time multi-person tracking precedent on the same board (Huang et al.).
* Low absolute cost at €108.89 incl. VAT for the 4GB variant, keeping the initial hardware ask small given no project budget is approved yet (Finance and Risks).
* Standard GPIO/UART-over-USB interface and a mainstream Linux (Debian-based) ecosystem, satisfying the host-interface-compatibility criterion without added interface hardware.
* 4GB is comfortably enough for the host's own reduced job (receiving a small classified result, running the microphone array, bridging to the network), since classification itself runs on the IWR rather than the host.

Cons::
* No onboard GPU/NPU acceleration; ProbRadarM3F can still run on CPU, but whether it stays inside the latency budget on this board is unproven, and it would need the board to fall back to ingesting the raw point cloud rather than the lean classified stream.
* Barral et al.'s reported USB bandwidth constraint is an open risk, unconfirmed against this project's own data rate, and would only actually matter if that same fallback is triggered.

[[rpi5]]
== Raspberry Pi 5

A quad-core, out-of-order Cortex-A76 @ 2.4GHz with 8GB RAM, Gigabit Ethernet with PoE+ support, WiFi, USB 3.0, PCIe 2.0, and a 40-pin GPIO/UART header, €192.38 incl. VAT at current link:https://www.kiwi-electronics.com/en/raspberry-pi-5-8gb-11580[Kiwi Electronics] (NL) listings.

No gathered source pairs this specific board with the IWR6843 family; it shares the same GPIO/UART interface and Debian-based Linux stack as the wider Raspberry Pi family, so integrating this project's sensor-parsing and classification software needs no new interface work.
Its out-of-order CPU cores and doubled RAM give real headroom for the ProbRadarM3F keypoint fallback (~30-50ms estimate) and for running the microphone array's beam-steering concurrently, though neither is benchmarked on this exact pipeline yet.
PCIe 2.0 and USB 3.0 also leave room for a future accelerator add-on, if CPU-only inference on this board still proves insufficient.

Pros::
* Meaningfully more CPU and memory headroom than the primary classification approach needs on its own, a margin against the ProbRadarM3F fallback or concurrent microphone-array beam-steering.
* Same GPIO/UART interface and Linux ecosystem as the wider Raspberry Pi family, so no new interface work is needed.
* PCIe and USB 3.0 leave room for a future accelerator add-on if CPU-only inference proves insufficient.

Cons::
* No gathered source pairs this specific board with the IWR6843 family.
* €192.38 incl. VAT is a real expense given no project budget is approved yet (Finance and Risks).

[[jetson-orin-nano]]
== NVIDIA Jetson Orin Nano Super Developer Kit

A 6-core Cortex-A78AE @ 1.7GHz paired with a 1024-core Ampere GPU and 32 tensor cores (up to 67 TOPS INT8), 8GB LPDDR5, 7-25W power envelope.
No EUR-market listing was found at a major distributor; converting Electrokit's (SE) listed 5,329 SEK incl. VAT gives approximately €465, consistent with Aetherix's (NL) directly listed €468.47, so €465-470 is used as the working estimate.

No gathered source pairs this board, or any Jetson model, with the IWR6843 family or with the ProbRadarM3F keypoint model specifically.
The case for it is inferred, not demonstrated: ProbRadarM3F (<<probradarm3f2024>>) is a PyTorch/CUDA model, and Jetson's CUDA and TensorRT stack is the standard embedded deployment target for that model class in general.
That is a reasonable inference from how such models are normally deployed, not a result specific to this project's use case.

Pros::
* Only candidate with GPU/tensor-core acceleration, the class of hardware the ProbRadarM3F keypoint fallback would most plausibly need if the simple threshold approach underperforms.
* Same GPIO-class headers and USB/networking interfaces as the SBC candidates, so the sensor interface itself is no harder to integrate.

Cons::
* No literature or documented case pairs it with this project's specific sensor or classification model.
* At ~€465-470 incl. VAT, this is a substantial per-unit cost against Finance and Risks' unapproved budget.
* A 7-25W power envelope and active cooling requirement, a consideration if the board needs to sit inside or close to the Holobox housing.
* Justified only if the simple threshold classification approach turns out to be insufficient; committing to it now would be pre-paying for a capability not yet shown to be needed.

[[compute-recommended-approach]]
== Recommended Approach

The Raspberry Pi 4 Model B, 4GB variant, is recommended as the starting platform.
It is the only candidate with a literature precedent for the exact split this project plans to use, a TI IWR6843-family radar handling onboard tracking with a paired host running downstream classification and output (Barral et al.), reinforced by a separate real-time-tracking precedent on the same board (Huang et al.).
4GB is sufficient because the host's own job is narrower than that precedent's architecture: classification runs in the IWR's own onboard firmware, not on the host, so the host only needs to receive a small classified result, run the microphone array's beam-steering, and bridge both to the network (Introduction).
The 8GB variant exists and costs little more, but there is no overhead case to pay for it now against a workload that does not approach 4GB in the first place.
It is also the cheapest board reviewed, so no cost trade-off is being made against a lower-cost alternative.
Finance and Risks reports no project budget has been agreed with MindLabs yet, so starting with the cheapest board that already has a working precedent, rather than paying up front for headroom the current design does not need, keeps the initial ask to the company mentor small.

This is a starting-point recommendation, not a final hardware order; as with the sensor choice in Candidate Sensor Technologies, it still needs mentor approval before anything is purchased (Finance and Risks).
Two risks carry forward into the bench-testing stage set out in Research Approach: Barral et al.'s reported USB bandwidth constraint, unconfirmed against this project's own point-cloud data rate, and whether the Pi 4 has spare CPU cycles once the microphone array's beam-steering runs alongside classification (Compute Platform Implications).
Neither is a RAM problem: the bandwidth constraint is about the UART/USB link, and the concurrent-workload question is about CPU cycles, not memory capacity, so paying for 8GB now would not address either.

If bench measurement shows either risk is real, the Raspberry Pi 5 is the documented next step: same interface and software ecosystem as the Pi 4, so the fallback does not mean re-validating a different platform, at roughly double the compute headroom (per published Geekbench 6.2 figures: ~2.2-2.4x over the Pi 4) for about a 77% cost increase over the Pi 4 (4GB).
The Jetson Orin Nano Super Developer Kit stays a further fallback specifically for the ProbRadarM3F keypoint model, if the primary top/bottom-point classification approach turns out not to be accurate enough (Candidate Sensor Technologies); it is not adopted now because that model's need is itself unconfirmed, and it is the most expensive and highest-power candidate reviewed, at roughly 5x the Raspberry Pi 4 (4GB)'s cost.
